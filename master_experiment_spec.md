# Master Implementation Spec — API–Excipient Compatibility Model v2
### (Multi-Encoder, Swappable-Architecture Edition)

**Audience:** an AI coding agent with zero prior context on this project. Everything needed to implement the full system from an empty directory is in this document. Do not assume any file already exists.

**Domain:** predict whether a pharmaceutical Active Ingredient (API) and an Excipient are chemically **Compatible (0)** or **Incompatible (1)**, from their SMILES strings alone (plus 2D physicochemical descriptors computed from those SMILES). This is a binary classification task on a severely imbalanced dataset (~9–10% positive/incompatible class).

---

## 0. Read Me First

- This spec defines an architecture where the **molecular encoder is a config-selectable module**. Changing one config field (`encoder`) must be sufficient to switch the entire model between encoder types, with the rest of the pipeline (data loading, splitting, descriptors, loss, training loop, evaluation, CV) untouched.
- Build everything behind flags with sane defaults, never hard-code a single encoder's assumptions into shared code.
- Implement in the **phases listed in Section 14, in order**. Do not skip ahead. After each phase, run the smoke test specified for that phase before moving on.
- Every numeric hyperparameter in this document is a *default*, not a suggestion to omit — put it in the config with exactly this value unless a section says "tune this."
- All dimensions given below assume `proj_dim = 128`, `num_descriptors = 21`, `desc_proj_dim = 24`, `batch_size = 64`. If you change any of these, propagate the change through every downstream dimension calculation shown here (the formulas are given so this is mechanical, not guesswork).

## 1. Problem Statement & Data

- Input: `data/start_dataset.csv` with columns `API_CID, Excipient_CID, Outcome1, API_Smiles, Excipient_Smiles`.
  - `Outcome1`: 0 = compatible, 1 = incompatible (this is the label).
  - Some `Excipient_Smiles` may contain multi-fragment SMILES (salts, e.g. `[N+](=O)([O-])[O-].[K+]`) — these are valid single "molecules" (ionic compounds) and must be handled as such, not rejected.
  - Class balance: ~90% compatible / ~10% incompatible. Do not assume balance anywhere in the pipeline; every component below is designed for this imbalance.
- Output of the whole system: a scalar probability of incompatibility per (API, Excipient) pair, plus a tuned decision threshold.

## 4. Data Pipeline

### 4.1 Raw data schema
As given in Section 1. Load with `pandas.read_csv`.

### 4.2 Leakage-safe splitting (`data/data_split.py`)

Naive random splitting leaks: the same API (or a salt/hydrate variant of it) can appear in both train and test, inflating metrics. Use **API-level Butina clustering** so structurally similar APIs never straddle a split.

Exact algorithm:
1. Get the set of unique `API_Smiles` values.
2. Compute a 2048-bit Morgan fingerprint (radius=2) for each unique API via RDKit (`rdkit.Chem.AllChem.GetMorganFingerprintAsBitVect(mol, 2, nBits=2048)`).
3. Compute the full pairwise Tanimoto distance matrix (`1 - TanimotoSimilarity`) between all unique API fingerprints.
4. Run RDKit's Butina clustering (`rdkit.ML.Cluster.Butina.ClusterData`) with `distThresh=0.15` (i.e., APIs with similarity ≥ 0.85 are forced into the same cluster).
5. Assign every row of the dataset a `cluster_id` = the cluster index of its API.
6. Run `sklearn.model_selection.StratifiedGroupKFold` (5 splits) using `groups=cluster_id` and `y=Outcome1`, to get a 60% train / 20% val / 20% test split that (a) never splits a cluster across sets and (b) keeps the ~10% positive rate roughly constant in every split. Concretely: take 3 folds as train, 1 fold as val, 1 fold as test (or equivalent — the exact fold arithmetic is up to you, but the 60/20/20 ratio and the "no cluster crosses a split boundary" invariant are both required).
7. Write `train.csv`, `val.csv`, `test.csv` under `data/`.
8. Log cluster statistics (number of clusters, number of APIs merged into multi-member clusters) to `data/splitlog.log`.

This split is **fixed for the entire project** — every encoder/architecture experiment must train/validate/test on these exact same three CSVs so results are comparable. Generate them once, never regenerate mid-experimentation.

### 4.3 RDKit descriptor computation (`src/descriptors.py`)

For every unique API and every unique Excipient, compute this exact 21-column vector from its SMILES (via RDKit):

```
MolWt, MolLogP, TPSA, NumHDonors, NumHAcceptors, NumRotatableBonds,
NumAromaticRings, RingCount, FractionCSP3, HeavyAtomCount,
fr_NH2, fr_NH1, fr_ester, fr_amide, fr_aldehyde, fr_ketone,
fr_phenol, fr_ether, fr_epoxide, fr_halogen, fr_COO
```

All of these are direct RDKit `Descriptors.<Name>` or `Descriptors.fr_<name>` functions except `FractionCSP3` (`rdMolDescriptors.CalcFractionCSP3`) — use RDKit's built-ins, do not hand-roll.

- Save one row per unique `API_CID` to `data/api_descriptors.csv`, one row per unique `Excipient_CID` to `data/excipient_descriptors.csv`.
- Compute the **mean and std of each of the 21 columns using only the training-split rows** (join train.csv's API_CIDs/Excipient_CIDs against the descriptor tables), save to `models/descriptor_norm_stats.json` as `{api_mean: [...], api_std: [...], exc_mean: [...], exc_std: [...]}`.
- At load time, normalize every descriptor vector as `(x - mean) / (std + 1e-8)`. Never fit normalization stats on val/test data.

## 5. Axis A — Encoder Branch (swappable)

### 5.1 Common interface contract

Every encoder module must implement one function:

```python
def encode(smiles_batch: list[str]) -> EncoderOutput
```

Where `EncoderOutput` is one of two shapes:

- **Sequence-capable** encoders return `(token_embeddings, pooled_embedding, token_mask)`:
  - `token_embeddings`: `[B, L, D]` float tensor — one embedding per atom/token (padded to the batch's max length `L`).
  - `pooled_embedding`: `[B, D]` float tensor — a single whole-molecule embedding.
  - `token_mask`: `[B, L]` bool tensor, `True` = padding position (to be excluded from attention), matching PyTorch's `MultiheadAttention` `key_padding_mask` convention.
- **Fixed-vector** encoders return only `pooled_embedding: [B, D]` (no sequence, no mask). `D` varies by encoder and must be reported via an `output_dim` property.

`src/encoders/__init__.py` exposes a registry:

```python
ENCODER_REGISTRY = {
    "molformer": MolFormerEncoder,
    "pretrained_gin": PretrainedGINEncoder,
    "chemberta": ChemBERTaEncoder,       # optional, Section 5.4
    "fixed_vector": FixedVectorEncoder,  # Section 5.5
}
```

`config.encoder` selects the key. `model.py` must branch on `encoder_module.is_sequence_capable` (a bool attribute every encoder class sets) to decide whether to build the cross-attention path (Section 6.1) or fall back to concat-only fusion (Section 6.2). **Never hard-code an encoder name inside `model.py`.**

### 5.2 A1 — MoLFormer-XL (existing baseline, frozen transformer)

- Model: `ibm/MoLFormer-XL-both-10pct` from HuggingFace, loaded via `AutoModel.from_pretrained(..., deterministic_eval=True, trust_remote_code=True)` and its matching `AutoTokenizer`.
- **Frozen**: `requires_grad_(False)` on all its parameters. It is never fine-tuned; only the layers built on top of it train.
- Output dim `D = 768`.
- Tokenize each SMILES string, run through the model, take:
  - `token_embeddings` = last hidden state, excluding special tokens, `[B, L, 768]`.
  - `pooled_embedding` = the model's pooler output, `[B, 768]`.
  - `token_mask` = inverse of the tokenizer's attention mask (True where padded).
- Cache embeddings by SMILES string in an in-memory dict inside the encoder object (many pairs share the same API or Excipient) to avoid recomputation. This encoder is used for **both** API and Excipient sides, via two separate projection heads downstream (Section 6), not two separate encoder instances — one frozen MoLFormer is shared for both molecules to save memory.

### 5.3 A2 — Pretrained GIN encoder (RECOMMENDED new Axis-A option)

**Why this one:** every encoder tried so far in this project (MoLFormer, mol2vec, PubChem fingerprints) reads the SMILES *string* — a linear, arbitrary serialization of the molecular graph. None of them sees molecular topology (ring systems, branching, connectivity) directly. A pretrained **graph neural network** does, and graph-based encoders have a strong track record beating string-based transformers on small molecular-property datasets specifically because they encode an inductive bias (message passing over the actual bond graph) that a string transformer has to learn implicitly from data it doesn't have much of here (~2,000 training rows). We deliberately are **not** recommending Uni-Mol (needs 3D conformer generation, which is unreliable for the ionic/multi-fragment excipient SMILES in this dataset — many excipients are inorganic salts with no meaningful 3D conformer) or GROVER (heavier, harder to integrate cleanly). The best practical choice is the **pretrained GIN from Hu et al., "Strategies for Pre-training Graph Neural Networks" (ICLR 2020)**, self-supervised + supervised pretrained on ~2 million ZINC15/ChEMBL molecules, distributed via the `dgllife` library with a one-line loader. It is well documented, robust to disconnected multi-fragment SMILES (salts), and structurally slots into the exact same "token sequence + pooled vector" contract MoLFormer already uses — meaning the cross-attention fusion block does not need to change at all.

**Exact spec:**
- Architecture (already pretrained, do not modify): 5-layer GIN (Graph Isomorphism Network), hidden dimension 300 at every layer, batch normalization after each layer, ReLU activation, residual connections between layers (as in the original implementation).
- Node input features: atom type (up to 120 categories) + chirality tag (4 categories), each embedded to 300-dim and summed.
- Edge input features: bond type (6 categories) + bond direction (3 categories), each embedded to 300-dim and summed, added into the message-passing step.
- Load via:
  ```python
  from dgllife.model import load_pretrained
  from dgllife.utils import mol_to_bigraph, PretrainAtomFeaturizer, PretrainBondFeaturizer
  gin_model = load_pretrained('gin_supervised_contextpred')  # 5-layer GIN, 300-dim, frozen
  gin_model.eval()
  for p in gin_model.parameters():
      p.requires_grad_(False)
  ```
- SMILES → graph: `mol = Chem.MolFromSmiles(smiles)`; `g = mol_to_bigraph(mol, node_featurizer=PretrainAtomFeaturizer(), edge_featurizer=PretrainBondFeaturizer())`. Multi-fragment SMILES (salts) produce one DGL graph with multiple disconnected components — this is fine and correct; message passing simply does not cross fragment boundaries, matching the physical reality that the ions are separate species.
- Forward pass: `node_feats = gin_model(g, node_input_feats, edge_input_feats)` → `[num_atoms_in_batch, 300]`. Un-batch back into per-molecule padded tensors of shape `[B, L, 300]` (`L` = max atom count in the batch) to serve as `token_embeddings`, with a corresponding `[B, L]` boolean pad mask. This step (un-batching a DGL batched graph into a padded tensor) is standard — use `dgl.unbatch(g)` then pad with `torch.nn.utils.rnn.pad_sequence`.
- `pooled_embedding` = mean of each molecule's node embeddings (`dgl.mean_nodes` or manual masked mean) → `[B, 300]`.
- Output dim `D = 300`. Cache by SMILES string exactly like the MoLFormer encoder.
- This encoder is frozen (same rationale as MoLFormer: with ~2,000 training rows, fine-tuning a pretrained GNN end-to-end will overfit badly; only the projection/fusion/classifier layers on top should train).

**Architecture consequence of adding this encoder:** `config.molformer_dim` (768) must be generalized to `config.encoder_output_dim`, set automatically per encoder (768 for MoLFormer, 300 for GIN, see Section 10). Every place `model.py` currently assumes `768` as the input dim to the projection heads must instead read `config.encoder_output_dim`. No other architectural change is required — the CLS-token-prepend, bidirectional cross-attention, descriptor fusion, and classifier head are all encoder-agnostic once this one dimension is parameterized.

### 5.4 A3 — ChemBERTa (optional secondary sequence encoder)

Only implement after A1 and A2 both work end-to-end. Same interface as A1 (it's also a HuggingFace SMILES transformer): use `DeepChem/ChemBERTa-77M-MTR` (`AutoModel` + `AutoTokenizer`), frozen, output dim 384 (check the actual hidden size from the loaded config and set `encoder_output_dim` accordingly — do not hard-code 384 without verifying against `model.config.hidden_size`). Token embeddings = last hidden state; pooled embedding = mean-pooled last hidden state over non-padding tokens (ChemBERTa has no dedicated pooler head — do not assume one exists; verify against the loaded model's output object and mean-pool if `pooler_output` is absent).

### 5.5 A4 — Fixed-vector encoders (mol2vec / PubChem fingerprint / plain descriptors)

For any encoder that outputs one fixed-length vector per molecule with no atom-level structure (mol2vec 300-dim embeddings, PubChem fingerprint 881-bit vectors, or even just the 21-dim RDKit descriptor vector used alone as an "encoder"):

- `is_sequence_capable = False`.
- `encode()` returns only `pooled_embedding: [B, D]` (D = 300 for mol2vec, 881 for PubChem FP, configurable).
- No cross-attention is possible — `model.py` must route this encoder straight to the concat fusion path (Section 6.2), skipping the CLS-prepend and attention blocks entirely.
- Precompute these vectors once (they don't need a forward pass per batch — mol2vec and PubChem FP are typically precomputed and cached to disk, e.g. a CSV keyed by CID, loaded like the descriptor lookup in Section 4.3) rather than recomputed live.

## 6. Axis B — Fusion Strategy

### 6.1 Cross-attention fusion (only valid when the encoder is sequence-capable)

Exact spec, reused unchanged from the current best-performing configuration:

- Projection heads (applied identically to API-side and Excipient-side token embeddings and pooled embeddings, each with **separate weights** for API vs. Excipient):
  ```
  Linear(encoder_output_dim -> 256) -> LayerNorm(256) -> GELU -> Dropout(0.15)
  -> Linear(256 -> 128) -> LayerNorm(128) -> GELU
  ```
  (`proj_dim = 128`, `proj_dropout = 0.15`.)
- Prepend the projected pooled embedding as a "CLS" token in front of the projected token sequence: sequence length becomes `L+1`. Extend the mask with one extra `False` (non-padded) position for the CLS slot.
- Two learned placeholder parameters (`exc_placeholder: [1,1,128]`, `exc_global_placeholder: [1,128]`, both initialized `~N(0, 0.01²)`) substitute for the excipient branch when its SMILES is missing (an `exc_available` flag of 0 per-row triggers this). Zero out the real excipient sequence and splice in the placeholders at the CLS and first-token positions when `exc_available == 0`.
- Bidirectional multi-head cross-attention, 8 heads, embed dim 128, attention dropout 0.15, `batch_first=True`:
  - Excipient queries attend to API keys/values → `refined_exc`; residual-add and `LayerNorm(128)`.
  - API queries attend to Excipient keys/values → `refined_api`; residual-add and `LayerNorm(128)`.
  - Use `torch.nan_to_num` on attention outputs before the residual add (guards against an all-masked row producing NaNs).
- Take the CLS position (`index 0`) of each refined sequence as the whole-molecule structural embedding: `h_api_struct: [B,128]`, `h_exc_struct: [B,128]`.

### 6.2 Concat fusion (used for fixed-vector encoders, and as an ablation for sequence encoders)

- Skip the CLS-prepend and attention blocks entirely.
- Project the pooled embedding directly: `Linear(encoder_output_dim -> 256) -> LayerNorm -> GELU -> Dropout(0.15) -> Linear(256 -> 128) -> LayerNorm -> GELU`, giving `h_api_struct`, `h_exc_struct` directly (no attention refinement).
- Everything downstream (Section 6.3, Section 7) is identical regardless of which fusion path produced `h_api_struct`/`h_exc_struct`.
- Add `config.fusion: Literal["cross_attn", "concat"]`, defaulting to `"cross_attn"` when `encoder.is_sequence_capable` else forced to `"concat"`. Allow `"concat"` to be manually selected even for sequence-capable encoders — this is how Axis-B ablations (does cross-attention actually help over MoLFormer/GIN, for a fixed encoder) get run.

### 6.3 Descriptor fusion + interaction terms (always applied, independent of Axis A/B)

- Descriptor projection heads (separate weights for API vs. Excipient):
  ```
  Linear(21 -> 32) -> LayerNorm(32) -> GELU -> Dropout(0.15) -> Linear(32 -> 24) -> LayerNorm(24) -> GELU
  ```
  (`desc_proj_dim = 24`.) Gate with `config.use_descriptors: bool = True` — when `False`, skip this block and the concatenation below.
- `h_api = concat(h_api_struct[128], d_api[24])` → 152-dim (or 128-dim if descriptors disabled).
- `h_exc = concat(h_exc_struct[128], d_exc[24], exc_available_flag[1])` → 153-dim (or 129-dim without descriptors).
- `h_exc_core = h_exc[:, :dim(h_api)]` (truncate off the trailing `exc_available` scalar so shapes match for the interaction terms).
- `interaction = h_api * h_exc_core` (element-wise product), `difference = |h_api - h_exc_core|` (element-wise abs difference). Both same dim as `h_api`.
- `pair_vector = concat(h_api, h_exc, interaction, difference)`. With descriptors on: `152 + 153 + 152 + 152 = 609`-dim.

## 7. Classifier Head (shared across every encoder/fusion combination)

```
Linear(pair_dim -> 128) -> GELU -> Dropout(0.5)
-> Linear(128 -> 64) -> GELU -> Dropout(0.4)
-> Linear(64 -> 1)      # raw logit, no sigmoid
```
(`clf_hidden_dim = 128`, `clf_hidden_dim_2 = 64`, `clf_dropout_1 = 0.5`, `clf_dropout_2 = 0.4`.)

**Bias initialization (do this for every configuration, not just the baseline):** initialize the final `Linear(64,1)` layer's bias to `log(prior / (1 - prior))`, where `prior` is the true positive rate computed from `train.csv`'s `Outcome1` column at run time (do not hard-code a rounded constant — compute it fresh each run so it always matches whatever `train.csv` currently contains). This prevents the model from wasting early epochs correcting for a naive ~50/50 assumption. Leave every other layer's initialization at PyTorch defaults.

## 8. Axis C — Loss Functions

All operate on raw logits (apply sigmoid internally, never pre-apply it). `config.loss: Literal["bce","weighted_bce","focal","asl"]`.

1. **`bce`** — plain `torch.nn.functional.binary_cross_entropy_with_logits`, no weighting. This is the control/floor baseline.
2. **`weighted_bce`** — same, with `pos_weight = (num_negatives / num_positives)` computed from the training split, passed to `binary_cross_entropy_with_logits(..., pos_weight=...)`.
3. **`focal`** — standard binary focal loss: `L = -alpha * (1-p_t)^gamma * log(p_t)`, with `p_t = p` if `y=1` else `1-p`. Defaults: `focal_gamma = 2.0`, `focal_alpha = 0.25`.
4. **`asl`** (current best, keep as default) — Asymmetric Loss (Ben-Baruch et al. 2020):
   ```
   p = sigmoid(logits)
   loss_pos = -y * (1-p)^gamma_pos * log_sigmoid(logits)
   p_shift = clamp(p - clip, min=0)
   loss_neg = -(1-y) * p_shift^gamma_neg * log(1 - p_shift + eps)
   loss = mean(loss_pos + loss_neg)
   ```
   Defaults: `asl_gamma_neg = 4.0`, `asl_gamma_pos = 1.0`, `asl_clip = 0.05`, `eps = 1e-8`.

Every loss function must accept an optional `sample_weight: [B]` tensor (multiply the per-sample loss by this before the final mean), even if unused in Phase 1 — this is required by Axis D's weak-label expansion (Section 9) so it can down-weight synthetic rows without a second code path.

## 9. Axis D — Lookup-table augmentation (Phase 2, optional, implement only after Sections 4–8 are working end to end)

Purpose: exploit domain knowledge about *why* incompatibilities happen (specific functional-group reactions) rather than only pattern-matching on the raw dataset.

1. **Reaction lookup table** (`data/reaction_lookup.csv`): a small hand-built table of known API–excipient incompatibility mechanisms, keyed by functional-group SMARTS pairs. Starter table (extend as needed — this is domain knowledge, not something to derive from the training data):

   | mechanism | api_functional_group (SMARTS) | excipient_functional_group (SMARTS) |
   |---|---|---|
   | Maillard reaction | primary amine `[NX3;H2]` | reducing sugar (aldehyde/hemiacetal) `[CX3H1](=O)` or `[OX2H][CX4H1]([OX2H])` |
   | Ester/amide hydrolysis | ester `[#6][CX3](=O)[OX2H0][#6]` or amide `[NX3][CX3](=[OX1])` | strongly basic excipient (metal hydroxide/oxide) `[OH-].[Mg+2]`-type, or acidic excipient |
   | Metal-ion catalyzed oxidation | phenol `[OX2H][cX3]` or thiol `[SX2H]` | transition-metal salt (e.g. Fe, Cu, Mn ions) |
   | Acid–base salt displacement | carboxylic acid `[CX3](=O)[OX2H1]` | alkali/alkaline-earth salt of a weaker acid |
   | Schiff base formation | primary/secondary amine | aldehyde/ketone-bearing excipient |

   For each API/Excipient in the dataset, use RDKit `Chem.MolFromSmarts` + `mol.HasSubstructMatch` to flag which functional groups are present, then flag a pair as matching a given mechanism if the API side matches an `api_functional_group` and the Excipient side matches the paired `excipient_functional_group` for the same row.

2. **D2 — Weak-label expansion:** for API×Excipient combinations *not* present in `start_dataset.csv` but drawn from the same pool of unique APIs/Excipients already in the dataset, auto-generate a weak positive label wherever a mechanism match from the lookup table fires, add these as extra training-only rows with `sample_weight = 0.3` (vs. `1.0` for real labeled rows), passed through to the loss function's `sample_weight` argument (Section 8). Never add weak-labeled rows to val/test.

3. **D3 — Engineered mechanism features:** add one extra input dimension per mechanism in the lookup table (a binary "this pair matches mechanism X" flag), concatenated onto the `pair_vector` before the classifier head (Section 7). This changes `pair_dim` by `+num_mechanisms` — update the classifier's first `Linear` input dim accordingly.

4. **D4 — Auxiliary multi-task head:** add a second small head off `pair_vector` (before the main classifier, sharing its input): `Linear(pair_dim -> 32) -> GELU -> Linear(32 -> num_mechanisms+1)` (the `+1` is a "no known mechanism" class), trained with cross-entropy against the weak mechanism label wherever one is available (rows with no mechanism match contribute zero to this loss — mask them out). Total loss = `main_loss + aux_weight * aux_loss`, `aux_weight = 0.3` default.

Gate all of D2/D3/D4 behind independent config flags (`use_weak_labels`, `use_mechanism_features`, `use_aux_head`), each defaulting to `False` so Phase 1 experiments are entirely unaffected.

    # --- Axis A: encoder selection ---

    proj_dim: int = 128
    num_heads: int = 8

    proj_dropout: float = 0.15

    # --- Classifier head ---

## 11. Training Loop Spec

- Optimizer: `AdamW(lr=1.5e-4, weight_decay=8e-4)`.
- Scheduler: `ReduceLROnPlateau(mode="max", factor=0.5, patience=8)`, stepped on validation PR-AUC each epoch.
- Early stopping: stop if validation PR-AUC hasn't improved by at least `0.002` for `6` consecutive epochs; restore the best checkpoint by PR-AUC.
- Gradient clipping: `clip_grad_norm_(model.parameters(), max_norm=1.0)` before each optimizer step.
- Batch size 64, max 150 epochs.
- Balanced sampling: build a `WeightedRandomSampler` over the training set with per-sample weight `1.0 / class_count[label]`, `num_samples = len(train_dataset)`, `replacement=True`. Gate behind `config.use_balanced_sampler`; when `False`, use plain `shuffle=True`. **Never** apply this sampler to val/test loaders — those must always reflect the true class distribution.
- Seed everything (`torch`, `numpy`, `random`) from `config.seed` at the start of every run for reproducibility.

---

## 12. Evaluation Spec

- Metrics: PR-AUC, F1, MCC, Precision, Recall, Accuracy, confusion matrix — compute all of these, every run. Do **not** use accuracy as a stopping/selection criterion (10% positive rate makes it meaningless); PR-AUC is the primary model-selection metric, F1 and MCC are reported alongside it.
- Threshold tuning: after training, sweep decision thresholds from `0.001` to `1.0` in steps of `config.threshold_step` on the **validation** set, pick the threshold that maximizes F1. Apply that fixed threshold to the test set for final reporting (never tune the threshold on test data).
- 5-fold cross-validation harness (`src/cross_validate.py`): reuse the exact same Butina-cluster group assignments from Section 4.2 to build 5 stratified-group folds, train one model per fold with identical config, report mean ± std of every metric across folds. Every encoder/fusion/loss combination should eventually get a CV run, not just a single train/val/test split, before being declared better or worse than another combination.

## Appendix: Notes for future extension

- If GPU memory becomes a bottleneck when adding more sequence-capable encoders, note that both MoLFormer and the pretrained GIN are frozen — only the projection/attention/classifier layers hold gradients, so multiple encoders' cached embeddings could in principle be precomputed once to disk and reused across many downstream architecture experiments (fusion/loss/lookup-table ablations) without re-running the encoder forward pass every time. This is a worthwhile optimization once Section 13's ladder grows past ~10 combinations.
